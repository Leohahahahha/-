# Findings & Decisions

## Requirements
- Use two currently spare A6000 48 GiB GPUs while the existing LoRA resume occupies GPU 0.
- Train next-state first and sent-command second, automatically and only after the first exits successfully.
- Use the same two 39-episode whiteboard datasets and the established episode-level split: validation episodes 1, 7 and 17.
- Keep tactile input and 7D action + 6D K-frame wrist-wrench supervision.
- Start from the published Tabero 49999 parameter checkpoint.
- Implement full-parameter fine-tuning in new isolated configs; do not alter the active LoRA experiment.
- Do not start the new training; provide user-operated commands after code/tests are complete.

## Research Findings
- The active r32 LoRA run uses GPU 0; GPUs 1 and 2 were free at the latest host check, while GPU 3 was occupied.
- The existing paired launcher and configs already encode dataset pairing, split, normalization isolation, W&B grouping and checkpoint finalization rules that should be reused structurally.
- `TrainConfig.trainable_filter` is the complement of `freeze_filter`; setting `freeze_filter=nnx.Nothing` makes every parameter leaf trainable.
- The published Tabero 49999 architecture already contains PaliGemma/action-expert LoRA leaves plus the base tactile TCN. Using non-LoRA Gemma variants would change parameter names/shapes and cannot strictly restore this checkpoint. Full fine-tuning should therefore preserve the published architecture and update both its base and LoRA leaves.
- The current whiteboard rank16 factory adds new tactile LoRA leaves that are absent from Tabero 49999. For a clean exact full-parameter initialization, the new config should set tactile-prefix LoRA rank to zero and use the strict original Tabero loader; the full base tactile TCN remains trainable.
- With two visible devices and `fsdp_devices=2`, the mesh is `(batch=1, fsdp=2)`: large parameters and Adam states are sharded across both A6000s instead of replicated data parallel. Global batch 2 gives one sample per device and is the conservative fit target.
- EMA is already disabled on the Tabero lineage, avoiding another full model copy. Checkpoint persistence saves inference params separately plus train state/optimizer, so full-parameter checkpoints will be materially larger than the 5.3 GiB LoRA checkpoints; the output volume currently has about 873 GiB free.
- The real checkpoint callback fix requires `wait_for_checkpoint_on_save=True`; the new launcher should use the same fail-fast atomic-finalization contract.
- Abstract two-CPU-device sizing of the selected full-train state reports 3,353,275,152 trainable parameters, 12.492 GiB global float32 parameters and 24.984 GiB global Adam state. FSDP=2 reduces parameter+optimizer residency to about 18.763 GiB per GPU before gradients, activations and compiler temporaries. This supports trying 2x48 GiB with global batch 2, but only a real initialization/first update can prove peak-memory fit.
- Keeping checkpoints at 4k/8k/12k can consume roughly hundreds of GiB across both models because optimizer state is now full-sized; 873 GiB free is sufficient for the planned run but disk use must be monitored.
- Final host preflight: GPU 0 is occupied by the existing LoRA run; GPUs 1 and 2 each have about 48.5 GiB free and 0% utilization; GPU 3 is occupied. Pair name `full_ft_whiteboard_20260916` and both config-scoped run directories are collision-free.
- The first real full-FT launch uploaded W&B run `htwauln8`, restored all parameters, reported 3,353,275,152/3,353,275,152 trainable leaves and completed validation step 0. It OOMed before the first optimizer update: XLA reported a 37.53 GiB rematerialized computation and then failed to allocate another 18.76 GiB on both FSDP devices. Pair status is `failed/train_next_state`, exit code 1, with no numeric checkpoint and no sent-command run.
- The full-FT W&B run exists; it was absent during the first observation because both normalization jobs run before `wandb.init()`. It later synced config and validation before the OOM, so the W&B failure state is accurate.
- The LoRA next-state resume did not fail again. It recomputed 8000→12000 with finite updates, finalized a new atomic 12000 checkpoint at 23:25:12, synced W&B and automatically started sent-command run `rp8qw8sz`, which is actively training.
- LoRA W&B reused run ID `2u1yst8r`. The first attempt had already advanced the remote W&B step to 12001; therefore W&B rejected all resumed history at steps 8000–12000 as non-monotonic. This affects the resumed chart/history, not the local optimizer updates or finalized checkpoint.
- Selected the first two-card OOM mitigation: retain FP32 master parameters and true all-leaf training, but replace AdamW's full first/second-moment trees with scheduled SGD without momentum. Direct BF16 parameter storage was rejected because `1e-5`-scale updates can be lost when written into BF16 weights. The new optimizer retains global-norm clipping and the cosine schedule but has only a scalar schedule counter as optimizer state.
- The real two-GPU stateless-SGD run reached logged step 990 with finite updates. Five consecutive roughly-200-step action-loss means were 1.80433, 1.78132, 1.77312, 1.84836 and 1.75542; this is noisy and lacks a convincing monotonic trend. Mean gradient norms stayed near 14--15 under a clip threshold of 1.0, so nearly every update was strongly rescaled. Only step-0 validation exists; the process ended before step-1000 validation, so final convergence cannot be inferred.
- A three-device abstract AdamW FSDP probe gives 16.910 GiB persistent model+optimizer state per GPU. This is 4.418 GiB above ideal one-third partitioning because the token embedding and several 2048/4096-wide matrices cannot be divided by three and are replicated. Three GPUs may improve over two but are a high-risk, unproven fit rather than a guaranteed solution.
- At the latest check, the SGD process was absent, its log ended at step 990 with no traceback, and `nvidia-smi` could not communicate with the NVIDIA driver. This separates the process termination from the convergence discussion; a driver reset/failure is the leading hypothesis, but there is no accessible Xid/kernel evidence to prove the root cause.
- No `train.py` process remains. The concurrent LoRA sent-command run also stopped near logged step 4811 without a Python traceback; unlike SGD, it has a complete checkpoint 4000 and can be resumed after GPU-driver recovery.
- A later successful restart completed the full-SGD next-state run through atomic checkpoints 4000/8000/12000 and then correctly launched full-SGD sent-command. Sent-command failed before any optimizer update during its mandatory step-0 validation: both aggregate `action_loss` and total `loss` were NaN, and the finite-metric guard raised `FloatingPointError`. W&B run `88cd9jmz` is therefore accurately marked failed; this was not a W&B transport failure or an SGD update.
- The sent-command normalization JSON is finite, and a CPU check of the first train and first validation batches found all loader tensors finite. Normalized actions were within roughly [-2.47, 4.26] for the sampled train batch and [-2.45, 3.20] for the sampled validation batch. The remaining investigation must scan all validation batches and/or instrument model loss to locate the first non-finite batch.
- The complete 500-batch/1000-frame sent-command validation loader is finite; normalized action values span about [-5.394, 4.120]. The matched next-state validation loader is also finite and spans about [-5.307, 4.825], yet next-state completed 12k and final validation. This rules out direct input NaNs and weakens a simple magnitude-overflow explanation. Remaining hypotheses are a pattern-specific BF16 forward instability or a GPU/driver fault that preceded the later `nvidia-smi` communication failure.
- The completed next-state full-SGD run has atomic checkpoints 4000/8000/12000 and final validation action loss 1.639652. The failed sent-command run has no `metrics.jsonl` and no numeric checkpoint, because the guard fired during pre-training validation.
- The peer's screenshot matches this repo's AdamW betas and epsilon; weight decay 0 versus 1e-10 is immaterial for memory. Learning rate also does not change residency. This repo retains every trainable full-FT parameter in FP32 because only frozen leaves are cast to BF16; model `dtype=bfloat16` is compute dtype, not trainable-parameter storage.
- For 3.353B parameters, single-device DDP lower-bound residency is about 12.492 GiB FP32 weights + 12.492 GiB gradients + 24.984 GiB FP32 Adam moments = 49.968 GiB before activations. A reported stable 33 GiB after the first optimizer step therefore implies lower-precision/offloaded optimizer state or parameters, fewer trainable parameters, or a different measurement point. PyTorch Adam state lazy initialization before the first step is a specific measurement pitfall.
- The real failed AdamW run used `2e-6 -> 2e-7`, not the SGD run's `1e-5 -> 1e-6`. Increasing AdamW to the peer's `2e-5 -> 2e-6` may change optimization but cannot fix the OOM.
- The user confirmed the peer uses mixed precision. This supports the memory-layout explanation, but does not yet distinguish autocast-only BF16 compute from actual BF16/FP16 parameter, gradient and Adam-state storage; exact tensor dtype inspection after the first optimizer step is still required.
- The peer-side code review now states that most VLM/action-expert parameters are actually BF16, selected embeddings/LayerNorm/action projection/time MLP remain FP32, native `torch.optim.AdamW` is used, and there is no explicit FP32 master copy. This makes the 8-bytes-per-BF16-parameter estimate (weight, gradient, two moments) and roughly 26.1 GiB persistent core for 3.5B parameters plausible; 33 GiB with FP32 exceptions, activations and DDP buffers is reasonable. Exact optimizer-state dtypes after the first step remain the final confirmation.
- The config-owned mixed policy casts 3,283,869,040 trainable parameters to BF16 and keeps 69,406,112 sensitive parameters FP32. The actual FP32 paths are vision embedding, vision/Gemma norms, state/action/time projections, action output and the full tactile-prefix TCN; checkpoint-provided transformer LoRA leaves follow the BF16 default.
- With two-device FSDP, mixed parameters occupy about 3.199 GiB/device. The low-memory fallback uses about 6.399 GiB/device for mixed-dtype Adam moments and 3.199 GiB/device for mixed gradients, or 12.797 GiB/device total static state before activations. The selected FP32 train-state profile uses about 12.508 GiB/device for Adam moments and 6.267 GiB/device for gradients, or 21.975 GiB/device total static state before activations and compiler buffers.
- The user reports that their senior has already run the analogous BF16-parameter plus FP32-gradient/optimizer layout successfully. This is relevant empirical evidence for selecting that profile, but it is not proof of the current JAX/FSDP/XLA peak because framework buffer lifetimes differ. The lower-memory mixed-state profile remains available as a fallback rather than being deleted.
- The numerically sensitive scalar loss reduction, global gradient norm and clipping scale are also accumulated in FP32. The main profile now explicitly casts gradients and both Adam moments to FP32; `optax.apply_updates` casts the resulting parameters back to each parameter leaf's configured BF16/FP32 storage dtype.
- JAX autodiff returns cotangents with the trainable leaf dtype, so BF16 parameter leaves initially produce BF16 cotangents. The implemented FP32-gradient contract casts the complete gradient tree immediately after autodiff and before clipping/Adam; it guarantees FP32 optimizer inputs and storage, not FP32 accumulation inside every backward kernel. True FP32 backward accumulation would require FP32 master leaves or deeper custom primitives and would approach the previously OOMing layout.
- Direct BF16 parameter storage has no FP32 master copy, so the mixed profile uses `2e-5 -> 2e-6` rather than the failed full-FP32 run's `2e-6 -> 2e-7`; the latter can be too small relative to BF16 write-back resolution. The full-FP32 AdamW profile keeps the conservative lower schedule.
- The whiteboard train split has 11,125 anchors. With global batch 2, 12,000 updates correspond to about 2.16 data passes, 20,000 to about 3.60, and 20 nominal epochs to about 111,250 updates. Because adjacent 50-step chunks overlap heavily and there are only 36 training episodes, 20 epochs should not be assumed beneficial; checkpoint selection should follow validation plus offline physical metrics.

## Technical Decisions
| Decision | Rationale |
|----------|-----------|
| Preserve `gemma_2b_lora`/`gemma_300m_lora`, but train every leaf | This is the only strict shape-compatible way to start from Tabero 49999 while implementing full-parameter updates. |
| Remove only the added tactile LoRA overlay (rank 0) | The published base tactile TCN is restored exactly and becomes fully trainable; no random adapter leaves are introduced. |
| Two-device FSDP (`fsdp_devices=2`), global batch 2 | Minimizes per-GPU parameter/optimizer/activation memory on two 48 GiB cards. |
| New collision-safe `*_full_ft_sgd_12k` configs | Preserve the failed AdamW run's provenance and prevent accidental resume from a directory with no checkpoint. |
| Do not promise three-GPU AdamW fit | FSDP=3 replicates several large power-of-two tensors and leaves 16.910 GiB persistent state per card before gradients, activations and compiler buffers. |
| Use mixed BF16/FP32 AdamW with FSDP=2 for the next fit attempt | It reproduces the peer's persistent-state layout while FSDP further shards those states across the two A6000s. |
| Select FP32 gradients and both Adam moments for the main mixed profile | The user supplied successful peer-side evidence; exact JAX/FSDP sizing still leaves about 26 GiB/card outside the static state, subject to a real first-step check. |
| Preserve a `mixed_bf16_lowmem_adamw` fallback | Framework-specific activation and XLA buffer peaks may still exceed the remaining headroom even when a peer's implementation fits. |
| Keep the original FP32 path as a selectable config | The precision decision is reversible and does not require editing model code when more GPUs become available. |

## Issues Encountered
| Issue | Resolution |
|-------|------------|
| First abstract-memory probe treated a `NamedSharding` leaf as if it had a `.sharding` member | Corrected the estimator to call `NamedSharding.shard_shape()` directly; the second probe completed without allocating model buffers. |
| CPU loader check could not create a lock under the read-only `/data/.../cache` path | Re-ran with an isolated writable Hugging Face cache under `/tmp`; both sampled splits loaded successfully. |
