- The user removed the obsolete duplicate keyword and Python compilation now passes. Ruff also normalized the two new registration blocks, but because it was run against the entire previously-unformatted `config.py`, it introduced widespread formatting-only churn outside the experiment section. Do not revert with a broad checkout; first verify semantics and decide whether the noise is acceptable or needs a targeted cleanup that preserves all existing user changes.
- Existing `tabero_whiteboard_pair_test.py` covers only the old rank16/20k config names and old 20k launcher. It does not verify the new rank32/12k model fields, batch/eval/schedule values, collision-safe assets, or new launcher's final-step logic. New focused CPU contract coverage is required before issuing a training command.
- Orbax 0.11.13 exposes `CheckpointManagerOptions.enable_async_checkpointing` (default `True`). The project currently hardcodes a two-hour `AsyncOptions` timeout and has no TrainConfig switch. A backward-compatible fix can add a default-true config field, pass it through `train.py` and `initialize_checkpoint_dir`, and set only the two new r32/12k configs to false. Existing `CallbackHandler` implements both `save` and `async_save`, so it should support synchronous manager mode; this must be proven with a temporary CPU save test.
- Follow-up disproved the direct synchronous-manager plan in this environment: Orbax composite saves with `enable_async_checkpointing=False` wait indefinitely in the contracted-signal path. Minimal async-manager saves without the assets callback also time out in the Codex sandbox, matching the earlier inconclusive synthetic Orbax probe; this sandbox cannot validate actual TensorStore commits. The safe scoped design is therefore to retain Orbax's normal async manager, fix the assets callback so it does not invoke `jax.process_index()` via `asyncio.to_thread`, and make the new configs immediately call `wait_until_finished()` after each periodic save. This serializes training with checkpoint completion without entering the broken synchronous-manager path.
- Direct isolation showed `CallbackHandler.save()` completes quickly on the main thread, while the old `asyncio.to_thread(self.save, ...)` path hangs. The first `jax.process_index()` call from that worker thread is the supported code-level deadlock mechanism. The original `CommitFutureAwaitingContractedSignals` also added a signal dependency unnecessary for this local normalization callback. The fixed async callback performs the small callback on the current thread and returns no commit futures; bulk parameter writes remain managed by Orbax.
- Real r32 training invalidated the claim that the assets callback needed no contracted signal. Checkpoints 4000 and 8000 finalized, but final step 12000 failed with `FileExistsError` while Orbax's background directory-creation future attempted to create `12000.orbax-checkpoint-tmp-8`; the immediate assets callback had already created that parent via nested normalization output. This is a race introduced by the current-thread/no-future callback revision. The corrected design must retain `CommitFutureAwaitingContractedSignals` so the callback waits for Orbax item-directory creation, while moving only the `jax.process_index()` decision to the current thread and running `args.callback` (which contains no JAX call) in the contracted future.
- Current run state after this failure: next-state metrics reached update/validation 12000, complete checkpoints are 4000 and 8000, 12000 is temporary only, and sent-command never started. PID 556792 remains resident after the traceback, sleeping in `futex_wait_queue`, holding about 34 GiB on GPU 2 with 0% utilization; this is a shutdown hang rather than ongoing optimization. Its waiting parent shells prevent the launcher trap from updating `status.txt`, which remains stale at `running/train_next_state`. Same-config one-GPU resume from 8000 is topology-compatible after the callback fix, but the residual process must be interrupted first; do not delete or rename the 12000 temporary directory.

## Research Findings
- Relevant pair is `whiteboard_force_ab_20260915`; only the `next_state` run exists. No `sent_command` log/checkpoint/W&B run was found.
- No matching launcher, `scripts/train.py`, or W&B process appeared in the process listing, so the observed training process is no longer running in the visible host process namespace.
- First run ID is `h5gj1m6i`, started 2026-09-15 23:29:19. The W&B core recorded its parent process exiting at 2026-09-16 04:05:33 without a normal `wandb.finish()` sequence in the inspected local logs; this explains the W&B `crashed` state.
- Complete checkpoints exist at updates 4000, 8000, and 12000. Update 16000 exists only as `16000.orbax-checkpoint-tmp-12`, so it is not a finalized/resumable checkpoint yet.
- The train metrics file was last modified 2026-09-16 01:30:30 during the 16000 save. The W&B binary remained open/updated until 04:01:37 and parent-exit detection occurred at 04:05:33, indicating a long stalled or stuck shutdown/checkpoint interval before the process disappeared.
- `status.txt` says `state=complete`, `stage=train_next_state`, `exit_code=0`, but `updated=` is blank and the expected outputs contradict completion. Treat this status as a launcher-status bug or stale/misleading status, not proof of successful training.
- W&B logged one network timeout at 00:27:53, but training continued through at least update 15000 and later reached the 16000 checkpoint attempt. Therefore that timeout did not itself terminate training.
- Host `nvidia-smi` shows GPUs 0/1/3 occupied by other users and GPU 2 idle; none is owned by the Tabero run. This independently confirms the training is no longer active.
- The last displayed training line is step 16070; the machine-readable metrics record uses completed-update semantics and ends at step 16071. The last validation is step 16000 with action loss 0.293907 and total loss 0.072256. All finite checks remained healthy.
- Validation action loss reached its observed minimum 0.245179 at step 3000, then fluctuated upward to 0.293907 at 16000. This is a proxy metric trend, not a real-robot performance conclusion.
- The disk has 883 GiB free and only 3% inode use. The temporary checkpoint has roughly the same apparent size as completed checkpoints but lacks final atomic-commit manifests; size alone does not make it restorable.
- Supported diagnosis: the run stalled during Orbax async save/finalize at update 16000. The process later disappeared without a Python traceback. The exact external termination trigger is unproven because kernel/system logs are unavailable.
- The original checkpoint records a `(batch=2, fsdp=1)` device mesh, so this run was using two data-parallel GPUs, not parameter-sharded FSDP. Every inspected parameter/optimizer leaf has an empty partition spec (replicated); changing to one visible GPU changes data parallelism, not tensor shapes.
- The launcher explicitly permits 1 GPU, keeps `fsdp_devices=1` and global `batch_size=4`, and its one-GPU dry-run succeeds. On one GPU all four samples and activations reside on that GPU, so restore/config compatibility is expected but 48 GiB runtime memory fit remains unverified until initialization succeeds.
- Orbax 0.11.13 is installed. `CheckpointManagerOptions.cleanup_tmp_directories` defaults to false and this project does not override it, so the stale 16000 temporary directory is ignored rather than automatically deleted. `all_steps()` tracks finalized checkpoints only; the last usable step remains 12000.
- The project configures async checkpoint timeout to 7200 seconds. This unusually long two-hour wait is consistent with a save/finalize stall remaining silent for a long period.
- User confirms no tmux was used. Loss of ordinary SSH/VS Code terminal connectivity can send SIGHUP/close the controlling PTY and terminate foreground jobs; this is now a plausible explanation for the final 04:05 parent-process disappearance. It does not explain why training progress had already stopped at 01:30 during checkpoint finalization.
- Current host query identifies GPU 2 as fully idle (48,538 MiB free). A real restore-only probe on that card is the remaining way to verify two-device checkpoint to one-device reconstruction and actual memory fit without executing an optimizer update.
- The restore-only probe on GPU 2 failed before array restoration because current `restore_state` passes no target shardings. Orbax reported original devices `[0,1]`, current `[0]`, and required new shardings. Therefore the present code cannot directly resume this two-GPU checkpoint on one GPU; a small restore-path change is required first.
- VS Code remote-agent evidence resolves the network question: management connection disconnected at 01:00:55, waited a 3-hour reconnection grace period, extension host exited at 04:00:31, the grace expired/disposed at 04:01:01, the pair/status closed at 04:05:31, and W&B saw its parent exit at 04:05:33. This makes remote-session cleanup the supported final termination trigger.
- Training continued for about 29 minutes after the VS Code disconnect and the W&B API timeout was earlier still. Internet/W&B loss did not stop model computation; lack of tmux allowed later VS Code session disposal to kill the foreground process.
