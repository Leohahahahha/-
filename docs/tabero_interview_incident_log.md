日期表示问题被定位或形成可靠结论的日期，不一定是故障首次发生的日期。

状态定义：

- **已解决**：根因明确，修复及针对性验证已完成。
- **已缓解**：已有防护或绕过方案，但上游根因仍存在。
- **待验证**：实现已经完成，还缺训练、离线评估或真机实验验证。

## 1. Bash 多行粘贴触发 `free(): invalid pointer`

- **日期**：2026-09-02
- **状态**：已缓解，上游注入库仍需维护者修复。
- **现象**：在 VS Code 终端粘贴带反斜杠换行的命令时，Bash 直接 SIGABRT；单行命令正常。
- **排查过程**：先排除 Python、JAX 和 VS Code；在独立交互式 Bash 中用一条 `echo` 加换行即可稳定复现。分析 core dump 后，调用栈落在 `record_history_cmdline -> record_cmdline_core -> free`。
- **根因**：`/usr/lib/libpayload.so` 的命令记录注入逻辑把只读区的回退字符串 `"-"` 当作堆内存释放。它不是项目代码或 Python 依赖错误。
- **解决方案**：所有操作命令保持单行；复杂流程写入 shell 脚本后只执行一条脚本命令；向系统维护者提交最小复现、core stack 和库路径。
- **验证**：单行和脚本文件执行正常；交互式反斜杠续行持续稳定复现崩溃。
- **面试讲法**：强调“逐层缩小故障边界”。先从应用层降到空 Bash，再用 core dump 把问题定位到本机注入库，避免错误地重装深度学习环境。

## 2. Python 环境安装与项目打包连续失败

- **日期**：2026-09-02
- **状态**：已解决。
- **现象**：冻结依赖安装先后遇到 lockfile 与项目名不一致、Hatch 无法自动发现包、PyAV 14.4.0 尝试源码构建并缺少 FFmpeg 开发头文件。
- **根因**：项目被重命名后打包元数据没有同步；源码布局为 `src/openpi`，需要显式配置；当前平台没有 PyAV 14.4.0 的合适安装路径，而 14.2.0 有兼容 wheel。
- **解决方案**：修正项目打包配置，显式指定 `src/openpi`；使用兼容 LeRobot 的 PyAV 14.2.0 wheel；在 `/data` 建立隔离 Python 3.11 环境。
- **验证**：225 个依赖安装完成；Python 3.11.16、JAX 0.5.3、PyTorch 2.7.1、LeRobot 0.3.3 和 PyAV 14.2.0 可导入，选定 CPU 测试通过。
- **面试讲法**：依赖问题需要区分解析、打包和本地编译三个阶段，每个阶段用对应证据处理，不靠反复删除环境碰运气。

## 3. LeRobot 非连续 episode 子集索引错误

- **日期**：2026-09-02
- **状态**：已解决。
- **现象**：训练集和验证集按非连续 episode ID 划分，例如验证集 `(4,14,24)`；上游 LeRobot v0.3.3 的 episode 边界数组是子集相对索引，但查询时仍使用原始 episode ID，可能越界或跨 episode 取动作 chunk。
- **根因**：原始 ID 和子集位置混用。
- **解决方案**：增加本地数据集子类，将原始 episode ID 映射到子集位置后再查询边界；加载时裁剪不需要的大型列。
- **验证**：合成的非连续 episode 边界回归测试确认 action chunk 不跨轨迹；真实验证集长度和末尾 padding 与 Parquet 一致。
- **面试讲法**：强调数据管线中的“ID 语义”。shape 正确不代表样本属于正确轨迹，必须用边界断言测试。

## 4. 训练约 260 步出现 NaN 且没有可恢复 checkpoint

- **日期**：2026-09-03（故障运行开始于 2026-09-02）
- **状态**：根因未定；故障防护已完成。
- **现象**：`real_fr3_4gpu_3000_20260902_203541` 在 step 250 验证 loss 仍有限，step 251 日志正常，约 step 261 的 loss、grad norm 和param norm 同时成为 NaN。首次保存计划在 500 步，因此没有 checkpoint。
- **排查结论**：现有日志不能确定第一个坏 update，也不能证明是数据、梯度、优化器状态、混合精度或硬件导致。原训练循环在 host 检查前已经应用参数更新，发现 NaN 时健康状态可能已被覆盖。
- **解决方案**：在更新前后检查模型、梯度和优化器树；遇到非有限值拒绝该更新，保留更新前健康状态；保存失败 batch、首个坏叶子索引、`numerical_failure.json` 和可恢复 checkpoint，然后立即报错退出。
- **验证**：合成 NaN/Inf 测试确认坏更新不会写入健康状态；后续 3000 步恢复训练记录有限，但不能反推旧故障根因已经消失。
- **面试讲法**：明确区分“增强可观测性与可恢复性”和“证明根因”。没有原始坏 batch 时，不把猜测包装成结论。

## 5. v1 跨 episode 继承旧动作目标

- **日期**：2026-09-03；v3 于 2026-09-09 完成复核。
- **状态**：v3 数据标签已解决；采集端旧缓存的具体代码位置仍需公共采集文件确认。
- **现象**：离线曲线在 episode 开头出现 300～450 mm 动作跳变，真实 state 基本不动。
- **关键证据**：
  - v1 的 29 条轨迹中，28 条首帧 `action-state` 超过 50 mm；
  - 14 条首帧 action 七个维度完全等于上一轨迹的末帧 action；
  - episode 4 前 11 帧保持旧目标，位置差 423.359 mm，机器人 state 相对起点仅变化 0.0053 mm；
  - exporter 只是逐行转换原始 `action.pose7`，说明污染在原始采集 Parquet 中已经存在。
- **根因判断**：高度支持 episode reset 后动作缓存/心跳仍保留上一轨迹目标；缺公共 `record_episode` 源码，无法精确到采集端代码行。
- **解决方案**：v3 将监督明确定义为同一 episode 内 `actions[t] = state[t+1]`，并丢弃每条轨迹最后一个观测，彻底避免旧命令目标作为标签。
- **验证**：逐元素验证全部 29 条轨迹；v3 所有 action 都严格等于 v1 的下一 state。v1 有 527 帧位置差超过 50 mm、最大 456.515 mm；v3 为 0 帧、最大 45.501 mm。
- **面试讲法**：从图像异常回溯到 NPZ、Parquet、原始反馈和转换脚本，逐层证明跳变在哪一层首次出现；修复后用全量逐元素不变量验证，而不是只看几张曲线。

## 6. 轴角在 ±π 附近产生约 2π 数值跳变

- **日期**：2026-09-03 首次发现；2026-09-09 在 v3 全量量化并实现训练修复。
- **状态**：v3 训练路径已解决，等待新模型训练和评估。
- **现象**：连续两帧 rotvec 分量相差约 6.28 rad，看起来像末端旋转一圈；SO(3) 实际旋转通常不到 1°。
- **根因**：轴角表示在 180°附近不唯一。`+πu` 和 `-πu` 表示相同姿态，规范化转换会在分支两侧改变旋转轴符号。旧 `DeltaActions` 直接执行 `action_rotvec - state_rotvec`，把表示切换误当成真实旋转。
- **量化结果**：v3 有 114/6626 个一步标签发生分支切换，最大物理旋转仅 1.225°；旧分量相减却产生约 2π 残差。
- **解决方案**：v3 专用变换使用 `R_relative = inverse(R_state) * R_action`，模型输出后用 `R_action = R_state * R_relative` 恢复绝对姿态。位置仍用相对 XYZ，夹爪保持绝对单指坐标。
- **验证**：正反变换回归和 v3 CPU contract 测试通过；原始 Parquet 可保留轴角分支，因为进入训练前会转换为 SO(3) 最短相对旋转。
- **面试讲法**：不要把欧氏向量差直接用于非欧氏空间。姿态属于 SO(3)，损失和误差都必须尊重群结构。

## 39. 两卡FSDP混合精度全量AdamW策略

- **日期**：2026-09-17。
- **状态**：混合精度参数、FP32梯度和FP32 Adam状态主档，以及状态跟随参数的低显存备选档均已实现并通过CPU/抽象FSDP验证；用户报告师兄的相近布局已经真实跑通，但本项目尚未执行GPU编译和首个AdamW更新。

- **证据**：新策略的真实抽象参数树共有3,353,275,152个可训练参数，其中3,283,869,040个为BF16，69,406,112个为FP32。FSDP=2下每卡参数约3.199 GiB。主档把整棵梯度和Adam一/二阶矩设为FP32：每卡梯度约6.267 GiB、Adam状态约12.508 GiB，参数+梯度+状态静态小计约21.975 GiB，尚未包含激活和XLA临时buffer。低显存备选让梯度/状态跟随参数dtype，静态小计约12.797 GiB。用户明确报告师兄已验证前一种布局可以运行，这是选择主档的外部实测依据；但不是当前JAX/XLA程序的首步证据。训练集有11,125个frame anchors，global batch 2时12,000 update约等于2.16次数据遍历，20 epoch约需111,250 update。
- **根因或明确假设**：原两卡OOM的已证实原因是所有参数本身也为FP32，加上FP32梯度/Adam状态和XLA首步峰值超过48 GiB；当前主档仍保留FP32梯度/状态，但把约32.84亿个大参数改为BF16，从而释放参数和相关编译输出空间。师兄跑通的结果提高了可行性，但PyTorch/JAX、DDP/FSDP和编译器buffer生命周期不同，所以本项目仍必须用真实首步验收。20 epoch对只有36条训练轨迹且相邻action chunk高度重叠的数据很可能增加过拟合或遗忘风险，不能把epoch数直接等同于性能。
- **解决方案**：扩展config-owned `ParameterDtypePolicy`，分别配置参数叶子、梯度和优化器状态。`mixed_bf16_adamw`主档将PaliGemma/Action Expert/已有LoRA大叶子设为BF16，将norm、视觉embedding、state/action/time投影和触觉TCN设为FP32，同时在JAX autodiff返回后、裁剪和Adam之前显式把全部梯度张量转为FP32，并用Optax包装器保证Adam一阶和二阶矩都以FP32初始化和更新；`optax.apply_updates`后参数仍按各自配置写回BF16或FP32。这里的“FP32梯度”准确指优化器接收到和持有的梯度张量为FP32；BF16参数叶子的原始cotangent由JAX先以BF16产生，不能把后转换误写成全反向算子均以FP32累积。`mixed_bf16_lowmem_adamw`保留梯度/状态跟随参数的备选。两档均使用`2e-5→2e-6`、FSDP=2、global batch 2、严格Tabero 49999初始化、W&B和每4000步checkpoint。另保留`fp32_adamw`和`fp32_sgd`。启动脚本用`TABERO_TARGET_STEPS`独立控制步数，避免再修改脚本常量。
- **验证范围**：混合参数路径、FP32梯度转换、两份Adam状态初始化及一次更新后的dtype、BF16参数写回、FSDP抽象分片和启动器profile均通过CPU合同；主档与低显存档的每卡静态大小已分别计算。没有启动本项目GPU训练，故不能宣称两张A6000一定不OOM，也未验证BF16权重的实际非零更新比例、验证loss、离线指标或真机性能。
- **面试讲法**：我把“混合精度”拆成参数存储、梯度存储、优化器状态和数值归约四层。依据已有同规模实测，让大矩阵参数保留BF16以节省显存，而梯度、Adam两份动量及关键小模块保持FP32，再用FSDP切分状态；同时保留低显存备选，并用逐dtype统计与当前框架的首步峰值作最终验收。

- **证据**：[N0-TWAM §2.2.1](https://arxiv.org/html/2607.23783v1#S2.SS2.SSS1)预测触觉图像的VAE latent残差；其观察支路力场编码与未来生成支路分开，不可把预测latent称为已标定力场。[MoSS §3.3及A.2](https://arxiv.org/html/2604.23272v2)预测未来物理信号序列，硬件观测为AnySkin双侧30D向量及7D关节torque；[TA-VLA §5](https://arxiv.org/html/2509.07962v1#S5)在动作与关节torque数值拼接的空间加噪并分别计算flow loss，不是学习的torque latent目标。这里只核对代表实例，不足以声称哪种占全领域多数或性能一定更好。本地`aft_data.py:282–290`以未来样本marker最后槽减第0槽得到shear[H,396]；`aft_policy.py::AFTOutputs`反归一化并输出[H,198,2]、K系wrench[H,6]。当前TCN输出2048D是历史条件摘要，没有训练配套的2048D→shear重构decoder。
- **根因或明确假设**：混淆了Transformer内部特征宽度、历史条件特征和未来预测变量。396→512→396的专家入口/出口不意味着在512D latent上定义生成目标；2048D也不天然比396D更紧凑。latent或许能滤除噪声和保留任务结构，但没有重构/接触监督不能保证细小滑移和力变化被保留，这是待实验假设。
- **建议/处理**：当前用途是与在线真实反馈比较、解释局部滑移和力偏差，优先保持传感器信号空间的预测；触觉单位沿marker坐标契约，不把shear当N、mm或物理速度，力分为N与N·m两组。在线真实触觉用相同参考、点序、坐标方向及尺度构造差分；按采集时间对齐t0+k/10与预测，K系/零偏/统计一致，跳过缺失或无效目标。可计算逐点二维误差及左右局部/P95统计，分别计算三轴力和三轴力矩残差，避免直接给6D量混合的物理norm。融合门控前可用训练固定尺度标准化。latent对照如后续需要，应采用有重构/任务约束的编码器，并用固定版本的同一编码器处理预测和真实值；若编码历史窗口，两者窗口及mask也必须相同。可解码回396D物理信号与基线比较，不直接挪用历史TCN输出当单帧真值。
- **门控语义边界**：预测误差表达偏离预期，不等同于接触存在；正常接触可预测准确且误差很小。接触状态由校准真实反馈及任务相关信息判定，预测残差用于异常接触/滑移/偏离检测，触觉shear对纯法向接触可能不敏感。正常无接触/正常接触/滑移需分别估计误报漏报，阈值应结合噪声、预测horizon和生成不确定性。快层显著修改动作后，旧chunk的感知预测是原基础动作的预期，失配不必然是异常接触，应缩短可信窗口或重规划，不能强制追随旧预测。
- **验证范围**：检索并读原文上述方法/硬件章节，静态检查target、反归一化和TCN代码。未改变正在运行的训练，未测模型感知预测质量、传感器标定、接触门控、AE重构或真机效果。是否直接预测优于latent必须用同数据/split、H、主干、预算的配对实验，并评估物理预测误差、接触/滑移事件与门控误报漏报，而非只比较两个空间的训练loss。
- **面试讲法**：根据反馈用途选预测表示，而不是把内部embedding当传感器物理量；直接量保证可核对接口，latent需要额外的重构或任务证据。把接触存在、预测失配和快层干预区分开，才能设计可解释且可校准的反馈门控。

## 当前推荐的端到端排查顺序

1. **验证数据不变量**：episode 边界、`actions[t]` 语义、时间戳、单位、shape、finite、视频/触觉同步。
2. **验证动作几何**：位置使用米，姿态用 SO(3) 相对旋转，夹爪区分单指和总宽。
3. **绑定模型资产**：checkpoint、config、norm stats、conversion 和 prompt 全部记录哈希与 provenance。
4. **离线成对评估**：固定 anchors、noise、seed、horizon、split，报告毫米、角度、P95/P99/max 和越界率。
5. **Shadow 分层记录**：完整 chunk、action0、action[k]、当前 state、观测年龄、传感器时间和 chunk 切换。
6. **检查分布偏移**：相机视角、TCP、起始六自由度姿态、触觉参考网格和任务文本。
7. **最后才做真机执行**：持续使能、workspace、target jump、tracking error、rate limit、底层 watchdog 和硬件停止全部有效。

## 面试回答模板

可以按下面六句话组织每个案例：

1. **场景和影响**：系统处在哪一阶段，问题阻塞了什么。
2. **可复现现象**：给出最小复现和关键数字。
3. **最初假设**：列出两到三个候选原因，不提前下结论。
4. **证据链**：说明如何逐层排除，并指出决定性证据。
5. **修复和保护措施**：既修根因，也增加断言、日志、哈希或 fail-closed 防护。
6. **验证边界**：说明什么已经被测试，什么还需要训练或真机实验。

后续每次出现新问题，都应追加一个带日期的独立小节，并同步更新“问题总览”和状态。
